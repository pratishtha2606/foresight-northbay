# Project FORESIGHT — Demand & Inventory Intelligence
Zidio Development · Data Science & Analytics · Client: NorthBay Living

An AI-powered demand forecasting and inventory risk-scoring system: a reproducible
data pipeline, a backtested SKU-level demand forecast, a transparent stockout/overstock
risk layer, a Streamlit planning dashboard, and a FastAPI scoring service.

## The problem
NorthBay Living (a simulated D2C home & lifestyle brand) plans ~200 SKUs of inventory
on spreadsheets and gut feel. They stock out of best-sellers and sit on slow movers.
FORESIGHT turns their sales/inventory history into a forecast and an early-warning
system for what to reorder, what to clear, and what to leave alone.

## The data
Four simulated extracts modelled on a real D2C brand (`data/raw/`, generated by
`src/generate_data.py`, seed fixed at 42 for reproducibility):
- `sales_daily` — daily units sold, revenue, price, promo flag per SKU
- `sku_master` — category, subcategory, launch date, cost, price per SKU
- `calendar` — date, week/month/season, holiday flag, promo events
- `inventory_snapshots` — periodic on-hand/on-order stock, lead time, reorder point

Data is deliberately imperfect (duplicate rows, missing values, inconsistent category
labels) — see `reports/eda_memo.md` for the full data-quality log and findings.

## Setup & run (reproduces everything from raw data)
```bash
git clone <this-repo>
cd foresight
python -m venv venv && source venv/bin/activate      # optional but recommended
pip install -r requirements.txt

bash run_all.sh
# or step by step:
python src/generate_data.py    # simulate the client's raw extracts
python src/pipeline.py         # clean + unify -> data/processed/weekly_sku_demand.csv
python src/forecast.py         # backtest + forecast -> data/processed/forecasts.csv
python src/risk.py             # risk scoring -> data/processed/risk_scored.csv

streamlit run app/dashboard.py                 # planning dashboard, localhost:8501
uvicorn service.main:app --reload --port 8000  # scoring API, localhost:8000/docs
```

## Backtest result (WAPE, rolling-origin, 4 folds, 6-week horizon)
| | WAPE |
|---|---|
| Seasonal-naive baseline | **0.219** |
| FORESIGHT model (HistGradientBoosting) | **0.156** |

The model beats the baseline by **~29%** on out-of-sample folds it never trained on.
Rolling-origin backtesting is used throughout — the model is always trained on data
strictly before the test window, so no future information leaks into a feature.
Full fold-by-fold numbers: `data/processed/backtest_results.csv`.

## Key assumptions
- Forecast horizon: 6 weeks, weekly grain (client asked for 6–8 weeks).
- Safety stock target: ~80% service level over the SKU's lead time.
- Overstock threshold: more than 8 weeks of forward demand cover on-hand.
- SKUs with under ~10 weeks of history are excluded from backtesting and use a
  simple recent-average fallback rather than the full model (sparse-history risk,
  per Section 16.2 of the client brief).
- Data is a point-in-time extract, not a live feed — see "Out of scope" in the brief.

## Repository structure
```
foresight/
  data/raw/            # simulated client extracts
  data/processed/       # cleaned + modelled outputs
  src/
    generate_data.py   # synthetic data generator (stands in for the client extract)
    pipeline.py         # D1 — ingest, clean, unify
    forecast.py          # D3 — features, baseline, model, backtest
    risk.py              # D4 — stockout/overstock scoring
  app/dashboard.py       # D5 — Streamlit planning dashboard
  service/main.py         # D6 — FastAPI scoring service
  reports/
    eda_memo.md          # D2 — data-quality & EDA insight memo
    executive_readout.md # D7 — stakeholder readout
  run_all.sh
  requirements.txt
```

## Deploying (so D5/D6 have public URLs for submission)
- **Dashboard:** push to GitHub → [share.streamlit.io](https://share.streamlit.io) →
  new app → point at `app/dashboard.py` → deploy. Free, ~2 minutes.
- **Scoring service:** push to GitHub → [render.com](https://render.com) → new Web
  Service → start command `uvicorn service.main:app --host 0.0.0.0 --port $PORT` →
  deploy. Free tier works; note it needs `data/processed/*.csv` committed or
  regenerated on Render's build step (`bash run_all.sh` as the build command).

## Honesty note
The model beats the baseline on this dataset, and that result is reported as-is from
`backtest_results.csv` with a fixed random seed — nothing here is cherry-picked. If you
regenerate the data with a different seed, re-run the backtest and report whatever you
actually get, even if the baseline wins on some fold — that's the non-negotiable rule
of this engagement per the client brief.
